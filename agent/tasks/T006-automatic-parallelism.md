# T006 — Automatic-Parallelism Experiment and Evidence Collection

## Goal
Determine, through a controlled 4-step experimental ladder and multi-level observability on `macos-15` (arm64, 3 vCPUs), whether, where, and under what workload conditions J2 automatic parallelism improves `dupe` performance.

## Prerequisites
- **T002:** Phase 4 differential correctness complete and frozen.
- **T004:** Standard benchmark corpora and generator operational.
- **T005:** Interpreter and native baseline measurements established on `macos-15`.

## Controlled Experimental Ladder

To decouple pure computation parallelism from filesystem I/O constraints, T006 executes four distinct experiments:

```text
[T006-A] Known J2 Pure Parallel Workload (Control: sum(collect(1..2000000)))
   │
   ▼
[T006-B] Pure In-Memory Hashing (Isolate CPU/Hash)
   │
   ▼
[T006-C] Filesystem Read + Hash (I/O Boundary Entry)
   │
   ▼
[T006-D] Full dupe Pipeline (End-to-End Duplicate Workload)
```

### Experiment T006-A — Known J2 Parallel Workload (Control)
- **Input / Program:**
  ```j2
  data = collect(1..2000000)
  print(sum(data))
  ```
  *(Source: `https://j2-lang.org/docs/parallelism.html`)*
- **Purpose:** Verify that the native compiler, toolchain, and host runner actually lower and execute multi-core parallel code across the 3 cores.
- **Success Criterion:** Measurable speedup in compiled native mode over interpreted mode, establishing that parallel lowering is operational.

### Experiment T006-B — Pure In-Memory Hashing
- **Input:** Pre-generated byte buffers residing entirely in RAM.
- **Operation:** Loop calculating `hash.sha256(buffer)` for each buffer independently. No filesystem operations in the hot loop.
- **Purpose:** Determine whether J2's automatic parallelism recognizes and parallelizes the specific hash loop formulation without I/O noise.
- **Success Criterion:** Clear empirical separation between serial execution and multi-core native scaling.

### Experiment T006-C — Filesystem Read + Hash
- **Input:** Real files generated on disk.
- **Operation:** Loop reading bytes (`fs.read_bytes`) and hashing (`hash.sha256`).
- **Purpose:** Measure whether introducing filesystem syscalls and sandbox capability checks degrades or suppresses compiler parallelization.
- **Success Criterion:** Identification of whether storage read latency or memory copying attenuates compute parallelism.

### Experiment T006-D — Full `dupe` End-to-End Pipeline
- **Input:** Standard corpora (C1, C2, C4, C5, C6, C7).
- **Operation:** Full duplicate analysis execution (`discovery -> size filter -> hash candidates -> group -> output`).
- **Purpose:** Measure application-level wall-clock speedup and stage breakdown under realistic filesystem conditions.
- **Success Criterion:** Detailed bottleneck analysis across file count, size distribution, and duplicate ratio.

## Parallelism Observability Hierarchy

1. **Level 1 — Compiler IR & Backend Inspection (`j2 emit-native`):**
   Examine generated backend source for parallel loop constructs. *Note:* Emitted code inspection provides compiler-level evidence, but its operational performance impact must be verified via Level 2 measurements.
2. **Level 2 — Empirical Runtime Performance:**
   Compare wall-clock execution time against the serial-equivalent native baseline under identical repetition protocols.
3. **Level 3 — External OS Profiling:**
   Use OS-level profiling tools on developer hardware to trace syscalls and context switches.
4. **Level 4 — CPU Core Utilization:**
   Monitor multi-core CPU load percentages across available cores (up to 300% on 3-core `macos-15`).
5. **Level 5 — Result Determinism Check:**
   Verify bit-for-bit output JSON identity across all runs to ensure parallel execution does not introduce race conditions or non-determinism.

## Key Research Questions to Answer
1. Did the J2 compiler recognize the duplicate detection loop as safely parallelizable?
2. Did execution become measurably faster in compiled native mode?
3. Was the observed speedup consistent across repetitions?
4. Which specific operational phase ($T_{discovery}$, $T_{read}$, $T_{hash}$) exhibited performance variance?
5. Did OS page cache or disk I/O dominate the execution time?
6. At what workload dimensions (file count, file size, candidate density) did scaling plateau?
7. Is the parallel behavior reproducible across CI (`macos-15`) and developer hardware?

## Acceptance Criteria
1. Experiments T006-A, T006-B, T006-C, and T006-D fully implemented and executed.
2. Compiler evidence gathered via `j2 emit-native` for all tested loop structures and correlated with runtime timings.
3. Raw timing data, speedup ratios, and stage breakdowns recorded in machine-readable format.
4. Detailed research report produced answering all 7 key research questions with explicit evidence grades.
5. Honest reporting of any negative or neutral results where automatic parallelism failed to engage.
